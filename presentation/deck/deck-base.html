The Problem

When every test drives every step through the UI, the suite pays for it three ways.

Slow
Login, navigate, add to cart, fill forms — for every single scenario.
Flaky
Every UI step is a chance for timing, rendering, or selector failure.
Blurry failures
A red test says "checkout broke" — not whether it was the API, the state, or the DOM.

"In brightest day, in blackest night, no flaky test shall escape my sight."

A ring's power lies in the precision of the will behind it — and so do your tests.

Anatomy of an Atomic Test

One test, one run, two truths: the API contract and the rendered DOM.

SmallOne scenario proves one behavior. No 40-step journeys.
IndependentNo hidden coupling between "the API suite" and "the UI suite" — or between tests.
API-heavyThe API does the heavy lifting; the UI validates only what matters.

Atomic Scenario: Three Steps

Every scenario runs the same skeleton, enforced by a Template Method.

1 arrangeViaApi() Real HTTP calls Asserts the API contract itself: status, schema, business rule.
→
2 hydrateUi() State into the browser Injects API-produced state (token, session) and/or drives the real UI.
→
3 assertUi() One look at the DOM Asserts the rendered DOM reflects that exact state.
same order, every scenario

Atomic Scenario in Code

The step definition declares three steps. The class owns the order — and logs which phase a failure died in.

// checkout.steps.ts
AtomicScenario.for('checkout').run({
  arrangeViaApi: () => facade.seedCartViaApi(order),
  hydrateUi:     () => facade.completeCheckoutViaUi(order),
  assertUi:      () => facade.assertOrderConfirmation(expected),
});

// AtomicScenario.ts — the skeleton is fixed
run(steps: AtomicScenarioSteps): void {
  logStep(`[${this.slice}] atomic scenario`);
  runAtomicSteps({ ... }); // arrange → hydrate → assert
}
2 assertions, max.

The Assertion Budget

1 API claime.g. the placed order came back pending
1 UI claime.g. the rendered total is byte-for-byte the API-computed total

Anything beyond two is a second test wearing the first one's clothes.

Claims, Preconditions, Guards

Claim The behavior the scenario exists to prove. expect() / .should() — only inside assert* Counts toward the budget
Precondition What must hold for the claim to mean anything. precondition() — throws PreconditionError Doesn't count
Guard Waiting for the DOM to settle before reading it. .should('be.visible') on a ready marker Doesn't count

A broken arrange step reads as "Precondition not met" — it never masquerades as a product failure.

Hydration Strategies

Each slice uses what the live app actually allows — discovered against the real DOM, never assumed.

Auth · standard login Pure injection Token → localStorage → visit /catalog
Auth · locked out Pure real UI A failure state can only be reproduced, not injected
Catalog · 5 markets Pure injection token + countryCode → fresh boot re-derives the market state
Checkout · 5 markets Hybrid Real login + API-seeded cart + real form submit

Checkout Hydration

Real UI loginmarket picker + submit — exercised once, deliberately
→
Seed cart via APIcy.request POST /api/cart — no redundant catalog clicks
→
Real form + submitaddress, required field, payment, place order, confirm

The cart store rehydrates client-side after first paint.

Cypress's built-in retry-ability absorbs the wait — no cy.wait(), no hand-rolled polling.

The Limits of Injection

This works Real UI: fill the form, click place order, confirm. /order-success renders order-id + order-total — written by the confirm click itself.
This does not POST /api/checkout, then visit /order-success directly. A generic shell renders — no order-id, no total. There is no server fetch to fall back on.

When a slice can't honestly assert both API and UI, skip it — don't fake it. Orders stayed out of scope for exactly this reason.

When to reach for cy.prompt()

cy.prompt Basics

Natural-language steps, resolved by AI against the rendered UI — not against your selector registry.

·One batched call per business action, never per click
·2 calls per scenario × 5 markets = 10 calls per run
·Fits a 100-prompt/hour free tier with room to retry
// CyPromptCheckoutUiStrategy.ts
completeCheckout(order: CheckoutRequestData): void {
  const prompt = preparePrompt(checkoutPrompts,
    'completeCheckout', {
      pizzaId: order.items[0]!.pizzaId,
      address: order.address,
      requiredFieldValue: order.requiredFieldValue,
      name: order.name,
      phone: order.phone,
  });
  cy.prompt(prompt.steps,
    { placeholders: prompt.placeholders });
}
## completeCheckout

- Add the pizza with id {pizzaId} to the cart
- Go to the checkout page
- Enter {address} into the address field
- Enter {requiredFieldValue} into this country's
  required delivery-detail field (zip code,
  neighborhood, postal code, prefecture, or
  district, whichever this country uses)
- Select cash as the payment method
- Click the place order button
- Confirm the order

Prompts as Markdown

One sentence replaces a five-country strategy map plus five locator keys.

Editable by anyone who can read English — no code changes. preparePrompt() cross-checks every {token} both ways — a typo fails in a free unit test, not a billed Cloud run.

One Interface, Two Strategies

The step definition never knows which one is active — the composition root decides.

DeterministicCheckoutUiStrategy LocatorProxy + cy.get() — fast, exact, coupled to the selector registry.
CyPromptCheckoutUiStrategy cy.prompt() — coupled only to the rendered UI, no selectors at all. 
// cypress/support/e2e.ts — the composition root
const sc-camel-ui-strategy = Cypress.expose('UI_STRATEGY') === 'cyPrompt'
  ? new CyPromptCheckoutUiStrategy()
  : new DeterministicCheckoutUiStrategy(selectors, checkoutApi);

Nothing in the test code changes between these two commands — only the wiring in the composition root.

What the Demo Proves

Proven The deterministic path is coupled to a selector registry. The prompt path is coupled only to the rendered UI. cy.prompt never reads checkout.locators.json — breaking that file cannot touch it.
Not proven That cy.prompt survives a change to the app itself. The stronger version renames a real data-testid in the live DOM, forcing the AI to resolve by semantics. Riskier — but it proves what the slide claims.

On a slide those two claims read identically. Say the difference out loud.
